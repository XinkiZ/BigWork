## 1 职责概述
我负责把运行在 DEC VAX/Ingres 上的**遗留课程目录**接进新系统，并解决它"慢"的问题：
用独立只读账号保证只读约束、用中间层缓存把 8 秒级访问降到毫秒级、把访问模式与缓存状态做成可现场切换的演示开关；
同时主笔《接口文档》，并用脚本把我的优化效果量化出来。

## 2 具体工作项

### 2.1 遗留库与只读约束（代码 + SQL）
| 工作项 | 产出 | 说明 |
|--------|------|------|
| 遗留库模拟 | `db/legacy_init.sql` | 建 `legacy_catalog` 库与三张老式命名的表：`COURSE_TBL`（12 门课）、`PREREQ_TBL`（5 条先修关系）、`QUALIFY_TBL`（教授授课资格）；**刻意不建外键、全大写列名、字符主键**，保留遗留风格 |
| 只读账号 | `legacy_ro`（仅 `SELECT`） | 让"新系统不修改遗留数据"这条题目约束由**数据库权限物理保证**，而不是靠代码自律 |
| 独立数据源 | `LegacyDataSourceConfig`（`legacyJdbcTemplate`） | 与主库数据源并存，扫描查询互不影响 |

### 2.2 中间层与缓存（代码）
| 工作项 | 产出 | 说明 |
|--------|------|------|
| 适配器 | `LegacyCatalogAdapter` | 模拟经 Unix 服务器开放 SQL 接口访问 VAX 遗留库：一次拉取课程 + 先修 + 资格，组装成 `CatalogSnapshot`；可配置模拟延迟（默认 8000 ms） |
| 中间层 | `CatalogService` | `cached` 模式读 Caffeine 缓存（TTL 600 s），未命中才回源；**启动预热**避免首个用户等 8 秒；提供强制刷新 |
| 模式切换 | `legacy.mode = direct / cached` | 现场即可对比"优化前/优化后"，并用接口/日志给出依据 |
| 可用性开关 | `legacy.available` | 置 false 时抛 `LegacyUnavailableException`（503 `CATALOG_UNAVAILABLE`），演示"目录不可用则终止用例" |
| 缓存状态可观测 | `CatalogService.status()` + `/api/system/status` | 输出模式、是否已缓存、课程数、快照时间与加载耗时，便于运行检查时解释 |

## 3 关键数据（本人负责部分的实测结果）
| 场景 | 耗时 | 说明 |
|------|-----:|------|
| direct 直连遗留库 | 8055.5 / 8049.1 ms | 稳定约 8 秒，满足 ≤10 s 但余量有限 |
| cached 回源刷新 | 8026.3 ms | 缓存加载（含模拟延迟） |
| cached 命中 | 29.8 / 26.3 ms | 平均 28.1 ms |
| 加速比 | **286.6 倍** | 直连平均 ÷ 缓存平均 |
| 并发对照 | 缓存 50 并发 360.4 QPS vs direct 10 并发 1.2 QPS | 去掉中间层后吞吐退化约 300 倍 |

## 5 收获与不足
**收获**：
- 真正理解了"遗留系统集成"的工程含义：既要尊重它的物理形态（老式命名、无外键、慢），
  又要在应用层把它包装成现代接口；把只读约束交给数据库权限，比我写十行判断都可靠；
- 缓存不是"加了就快"：TTL、预热、刷新策略、未命中时的降级路径都要设计，否则第一个用户就是受害者；
- 用 4.4 的对照组数据讲清楚"为什么必须优化"，比一句"我们加了缓存"有说服力得多。

**不足**：
- 最初把缓存放在 Adapter 内部，导致 direct/cached 无法切换；重构为 `CatalogService` 中间层后才达成演示目标；
- 接口文档初版只写了成功响应，错误码与状态码映射是后补的，导致前端一度无法判断失败分支。
