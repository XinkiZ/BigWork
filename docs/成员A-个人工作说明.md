## 2 具体工作项

### 2.1 注册核心域（代码）
| 工作项 | 产出 | 说明 |
|--------|------|------|
| 库表设计 | `semester`、`course_offering`、`schedule`、`schedule_item`、`enrollment`、`grade` | 课表项用 `item_type`(PRIMARY/BACKUP) + `sort_order` 表达"主选 4 + 备选 2 及顺序"；`promoted` 标记备选补位 |
| 选课引擎 | `ScheduleService` | 暂存/提交/更新/删除课表；主选 ≤4、备选 ≤2；先修、满员、时间冲突校验；提交写入选课名单 |
| 满员实时通知 | 提交校验返回 `COURSE_FULL` | 在写库前判定已选人数，保证"通知发生在学生提交课表前" |

| 关闭注册工作流 | `CloseRegistrationService` | 单事务：状态校验 → 取消无教授班级 → 取消人数 < 3 班级 → 备选按序补位 → 二次取消（循环至稳定）→ 计算学费并登记计费 → 学期置 CLOSED |

| 接口实现 | `StudentController`、`RegistrarController`（关闭注册部分） | 统一走 `AuthUser` 取当前身份，杜绝"传入他人 ID"的越权入口 |
| 测试 | `ScheduleServiceTest`（11）、`CloseRegistrationServiceTest`（6） | 覆盖先修/满员/冲突/上限/注册关闭/目录不可用/删除与更新课表/补位顺序/补位失败/重复关闭 |

## 4 收获与不足
**收获**：
- 体会到"契约先行"的价值：先把 `CourseOfferingView`、错误码、时序图定下来，6 个人并行才不互相踩；
- 关闭注册让我理解了批量业务的难点不在"删数据"，而在**顺序与收敛**：先取消、再补位、补位后还要再取消，
  必须循环到稳定状态，且整个过程必须原子；
- 学会了用"至少 3 人"这类业务阈值反推测试数据设计（种子数据里预置 0 人班、1 人班、无教授班）。

**不足**：
- 早期把"满员通知"设计成写库后校验，后来改为提交前校验——说明我对"实时通知"这条需求的第一遍理解偏了；
- 设计文档的类图初稿过于贴近数据库表，忽略了题目 UML 中 `Transcript`、`CourseCatalogSystem` 这类
  概念类，后期才补上映射表。
