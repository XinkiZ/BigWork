# 学生选课注册系统 测试计划

**文档版本**：V1.0（2026-10-15 定稿）　**编写**：成员D　**评审**：成员A（组长）、全组
**配套文档**：《测试报告》（`docs/07-测试报告.md`）

---

## 1 目的与范围

### 1.1 目的
定义本系统的测试策略、测试对象、用例清单、通过准则与性能验证方法，使"系统是否满足需求"
有可复现的判定依据，而不是依赖演示时的直观感受。

### 1.2 测试对象
| 对象 | 覆盖内容 |
|------|----------|
| 后端服务（`backend/`） | 认证与权限、选课引擎、关闭注册工作流、计费与重试、教授授课与成绩、学生/教授信息维护、成绩单 |
| 接口契约（`/api/**`） | 请求/响应结构、错误码与 HTTP 状态一致性 |
| 遗留目录中间层（`legacy/`） | direct 与 cached 两种模式的行为与耗时、缓存刷新、目录不可用分支 |
| 前端（`frontend/`） | 三端页面功能走查、Win95 交互规范、破坏性操作二次确认、错误提示可读性 |
| 数据库脚本（`db/`） | 脚本可重复执行、种子数据覆盖边界场景（满员/不足 3 人/无教授/冲突/先修链/上学期成绩） |

### 1.3 不测试范围
- 真实财务系统的对接（以本机模拟服务替代）。
- 遗留库本身的性能（已固定为模拟 8 秒延迟，用于验证中间层优化效果）。
- 浏览器兼容性与移动端适配（验收环境为单机桌面浏览器）。

## 2 测试策略

| 层次 | 手段 | 工具 | 执行频率 |
|------|------|------|----------|
| 单元/集成测试 | 服务层与仓储层行为验证 | JUnit 5 + Spring Boot Test | 每次提交（`mvn test`） |
| 接口测试 | MockMvc 端到端调用 REST 接口，校验状态码与错误码 | MockMvc + `spring-security-test` | 每次提交 |
| 数据隔离 | 全部测试跑在 **`bigwork_test`**，`@Transactional` 自动回滚 | `src/test/resources/application.yml` | 每次提交 |
| 端到端功能走查 | 人工按演示剧本在三端界面操作 | 浏览器 + 前后端联调环境 | 每迭代结束 |
| 性能测试 | 并发压测 + 遗留目录直连/缓存对比 | `tools/perf-test.mjs`、`tools/legacy-compare.mjs` | I5、I6 |
| 健壮性测试 | 开关切换（目录不可用、计费不可用）、越权访问、ID 不存在、取消删除 | 接口 + 界面 | I5、I6 |

### 2.1 测试环境约定
| 项 | 值 |
|----|-----|
| 测试数据库 | `bigwork_test`（由 `db/init.sql` 创建并复制主库全量数据） |
| 遗留库 | `legacy_catalog`，测试配置中 `legacy.simulated-latency-ms=0` 以免拖慢用例 |
| 计费重试周期 | 测试配置 `billing.retry-interval-seconds=3600`，避免定时任务干扰断言 |
| 演示开关复位 | `AbstractIntegrationTest.resetDemoSwitches()` 在每个用例后复位 `legacy.mode=cached`、`legacy.available=true`、`billing.available=true` |
| 数据基线 | 重复执行 `db/init.sql` 即可恢复到统一演示基线（脚本幂等） |

## 5 性能测试方案

### 5.1 并发性能（`tools/perf-test.mjs`）
```bash
node tools/perf-test.mjs                                  # 默认 50/100/200 并发
node tools/perf-test.mjs --endpoint=student/catalog       # 指定被测接口
node tools/perf-test.mjs --levels=50,100,200 --rounds=3   # 指定并发梯度与轮数
node tools/perf-test.mjs --endpoint=student/schedule      # 课表查询接口
```
- 机制：脚本以演示学生账号登录获取 JWT，然后按 `concurrency` 一次性发起并发请求
  （`Promise.all`），统计每轮耗时并计算 **P50 / P95 / 平均 / 最大 / QPS**；
- 每级并发执行 3 轮，取该级数据记录到 `tools/perf-result.json`；
- 记录项：并发数、轮次、成功数、失败数、P50、P95、最大值、QPS、被测接口。

### 5.2 遗留目录直连 vs 缓存（`tools/legacy-compare.mjs`）
```bash
node tools/legacy-compare.mjs
```
| 步骤 | 动作 | 记录项 |
|------|------|--------|
| 1 | 切换到 `cached`，调用 `/api/student/catalog` | 缓存命中耗时（预期 < 200 ms） |
| 2 | `POST /api/system/cache/refresh` 后立即调用目录 | 首次回源耗时（预期 ≈ 8000 ms） |
| 3 | 切换到 `direct`，连续两次调用目录 | 直连耗时（预期 ≈ 8000 ms/次） |
| 4 | 恢复 `cached` | — |
结果写入 `tools/legacy-compare-result.json`，并计算**加速比**（直连耗时 / 缓存耗时）。

### 5.3 2000 并发指标的外推方法（说明性验证）
题目要求"最高支持 2000 用户同时访问中央数据库、500 用户同时访问本地服务器"。本机为
单机开发环境（单 JVM + 单 MySQL 实例），无法真实产生 2000 并发连接，因此采用：
1. 以 50/100/200 并发实测数据为基线，观察耗时随并发增长的曲线形态
   （线性 / 次线性 / 出现拐点）；
2. 若 50→200 并发耗时增长近似线性，则按线性外推；若出现明显拐点，则报告拐点位置并说明
   瓶颈（CPU、连接池 30、MySQL 单实例吞吐）；
3. 明确标注外推值 **不是实测值**，并给出扩容路径（连接池调大、加只读副本、缓存命中率、
   水平扩展无状态服务）；
4. 同时说明本项目"中央数据库访问"由缓存层承担目录读流量，因此真实数据库压力的增长
   远低于用户数增长——这是题目要求中间层优化的直接收益。

## 6 进入准则 / 退出准则

### 6.1 进入准则
1. `db/init.sql` 与 `db/legacy_init.sql` 已在本机 MySQL 执行成功，`bigwork_test` 存在且数据与主库一致。

## 7 测试数据复位与缺陷管理

### 7.1 数据复位
- 每次性能测试或关闭注册演示后，重新执行 `db/init.sql` 即可恢复统一基线数据；
- 自动化测试因 `@Transactional` 自动回滚，不会污染 `bigwork_test`；
- 演示开关（目录模式/可用性、计费可用性）由 `AbstractIntegrationTest` 在用例后复位，
  手工演示时可在系统面板一键恢复。

### 7.2 缺陷分级
| 级别 | 定义 | 示例 | 处理时限 |
|------|------|------|----------|
| S1 致命 | 主流程不可用或数据错误 | 关闭注册把有效班级误取消；学费算错 | 立即修复 |
| S2 严重 | 用例分支不满足需求 | 满员未实时提示；越权未拦截 | 当日修复 |
| S3 一般 | 界面/文案/易用性问题 | 提示语不清晰；表格列宽异常 | 迭代内修复 |
| S4 建议 | 优化建议 | 增加排序、快捷键 | 视时间安排 |

## 8 测试风险与限制
| 编号 | 风险/限制 | 应对 |
|------|-----------|------|
| T-R1 | 本机无法产生 2000 并发，指标只能外推 | 明确标注外推性质，提供曲线与瓶颈分析（见 5.3） |
| T-R2 | 关闭注册为破坏性操作，反复执行会污染演示数据 | 每次执行前确认学期状态；必要时重跑 `db/init.sql` |

| T-R5 | 定时重试周期（30 秒）使自动化测试难以直接断言 | 测试配置把周期调大为 3600 秒，改为直接调用 `retryNow()`/`flushPending()` 断言 |
