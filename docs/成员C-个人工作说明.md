## 1 职责概述
我负责"谁能进系统、进来能做什么"：登录认证、三种角色的身份与权限隔离、学生/教授基础信息维护，
并把题目要求整理成可实现的《需求分析文档》。安全工作最容易出问题的地方是**越权**，
所以我把每个入口都做成"只认令牌里的身份"。

## 2 具体工作项

### 2.1 认证与授权（代码）
| 工作项 | 产出 | 说明 |
|--------|------|------|
| 登录认证 | `AuthService.login` | 支持学生（学号）、教授（P 编号）、管理员（用户名）三种账号；BCrypt 校验口令；失败统一提示"用户名或密码错误"（不泄露账号是否存在） |
| 令牌签发与解析 | `JwtService`、`JwtAuthFilter` | HS256，默认 720 分钟；过滤器解析后构造 `AuthUser(id, role, name, username)`，供业务层取当前身份 |
| 安全策略 | `SecurityConfig` | 无状态会话；登录与只读状态接口放行；其余需认证；401/403 均返回统一 JSON 错误体 |
| 角色隔离 | 控制器类级 `@PreAuthorize` | 学生/教授/管理员接口各自绑定角色；越权一律 403 |
| 归属校验 | 服务层校验 | 教授只能操作自己所授课程班；学生接口全部从 `AuthUser` 取本人 ID，**接口层不接收他人 ID 参数** |
| 账号数据 | `student` / `professor` / `registrar` 表 | 学号、教授编号唯一；口令仅存散列（种子账号口令统一为 `123456`/`admin123`，仅供本机演示） |

## 3 工作中的关键判断
| 判断 | 理由 |
|------|------|
| 权限校验放在控制器 + 服务两层，而不是只在前端隐藏按钮 | 前端隐藏只是体验，接口必须自己能挡住；测试用学生令牌直打管理接口验证 403 |
| 学生接口不接收 `studentId` 参数 | 从接口形态上消除越权入口——没有参数就没法传别人的 ID |
| 口令错误与账号不存在返回同一提示 | 避免账号枚举；两者都返回 401 |
| 有成绩记录的学生不允许删除 | 删掉会破坏成绩单与学业记录的完整性；用例中"删除"针对的是无关联数据的学生 |

## 5 收获与不足
**收获**：
- 理解了"认证（你是谁）"和"授权（你能做什么）"必须分层实现：JWT 解决前者，
  方法级注解 + 服务层归属校验解决后者；
- 用接口设计消除越权可能，比事后加一堆 if 判断更根本；
- 写需求分析时把每条业务规则编号（BR-x），后面设计、测试、验收都能引用同一编号，沟通成本大幅下降。

**不足**：
- 一开始把 `@PreAuthorize` 只放在方法上，遗漏了类级注解导致同类接口出现重复配置，后期统一为类级；
- 需求分析里对"成绩数据安全防护"的表述过于笼统，直到设计阶段才细化为"按登录身份过滤 + 无越权参数入口"。
