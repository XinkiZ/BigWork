## 3 关键设计判断
| 判断 | 理由 |
|------|------|
| 脚本幂等（`DROP DATABASE IF EXISTS` 重建） | 反复演示与测试复位要一键回到统一基线，同时避免"表已存在"错误 |
| 只读约束交给数据库权限 | 代码自律不可靠；只授 `SELECT` 从物理上保证"不修改遗留数据" |
| 错误码到 HTTP 状态的映射集中在全局异常处理器 | 语义化状态码由一处推导，业务代码只抛错误码，前后端约定稳定 |
| 主数据源显式 `@Primary`、遗留源 `@Qualifier` 注入 | 双数据源引入后自动配置推断存在歧义风险，显式声明消除隐患 |
| 测试库独立 + 事务回滚 | 集成测试不污染演示数据，`mvn test` 可随时重跑 |

## 5 收获与不足
**收获**：
- 幂等脚本是"可反复演示"的前提：`init.sql` 一台机器一把梭，验收现场不用赌环境；
- 把只读约束做成数据库权限，比写十行代码判断都可靠，答辩时也有物理证据；
- 种子数据要**为测试反推设计**（0 人班、1 人班、无教授班、满员班、先修链），否则用例根本覆盖不到边界。

**不足**：
- 双数据源的主源歧义风险到设计走查才暴露（DEF-03），后续才补上显式 `@Primary` 声明；
- 初版曾想把主库表直接照搬遗留库的字段命名，后来明确"主库现代化、遗留库保持原貌"两条路线，才把边界理顺。
