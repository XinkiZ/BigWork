## 2 具体工作项

### 2.1 计费域（代码）
| 工作项 | 产出 | 说明 |
|--------|------|------|
| 学费计算 | `BillingService.tuitionFor` + `TuitionProperties` | 学费 = Σ已注册课程学分 × 单价（默认 **500 元/学分**，可配置），用 `BigDecimal` 避免浮点误差 |
| 交易模型 | `billing_transaction` 表 | 字段：金额（正数应收 / 负数退费）、`tx_type`(INITIAL / ADJUSTMENT)、`status`(PENDING/SENT/FAILED)、`retry_count`、`last_attempt_at`、`description` |
| 交易登记与发送解耦 | `BillingService.create` / `attemptSend` / `flushPending` | 关闭注册事务内只登记 `PENDING`，事务提交后立即尝试发送；失败仅标记 `FAILED`，**不阻塞也不回滚业务** |
| 失败自动重试 | `@Scheduled` + `retryNow` | 默认每 30 秒扫描 `PENDING/FAILED` 交易重试，直至 `SENT`；提供手动重试入口（等价一次重试周期） |
| 单笔独立事务 | `attemptSend` 逐笔处理 | 一笔失败不影响其他笔；重试次数与最近尝试时间可查，用于运维与演示 |
| 模拟计费系统 | `BillingSystemClient` | 可用性可切换（`billing.available`），不可用时抛 `BILLING_UNAVAILABLE`（503） |
| 监控入口 | `/api/registrar/billing-transactions`（含手动重试） | 管理员可查看每笔交易状态、重试次数与时间 |
| 测试 | `BillingServiceTest`（4 个）+ `CloseRegistrationServiceTest` 中的计费断言 | 单价计算、发送成功、失败重试状态机、空扫描幂等 |

### 2.2 与关闭注册的接口约定
与成员A 冻结的契约：关闭注册在单事务内调用 `billingService.create(...)` 登记交易；事务提交后由控制器调用
`flushPending()` 立即发送一次；从此之后的重试完全由计费域的自己负责。这样"关闭注册"不必关心计费系统是否在线，
计费域也不必介入注册流程的事务。

## 5 收获与不足
**收获**：
- 学到"外部系统不可靠"是常态而不是异常：把登记与发送解耦、让失败可重试，
  业务侧就永远不会因为对方宕机而失败或长时间卡住；
- 理解了重试机制的关键细节：重试次数、最近尝试时间、单笔独立事务、幂等的扫描逻辑，缺一个都会在演示现场翻车；
- 用 `BigDecimal` 而不是 `double` 处理金额，是财务类代码的基本功。

**不足**：
- 最初想用循环加 `Thread.sleep` 在请求线程里等计费系统恢复，会导致接口长时间挂起；改为"登记 + 后台重试"后才合理；
- 重试周期早期写死在代码里（30 秒），后来改为配置项并在测试环境调大，否则自动化测试会被定时任务干扰。
