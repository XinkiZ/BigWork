## 2 具体工作项

### 2.1 选课引擎与课表
| 工作项 | 产出 | 说明 |
|--------|------|------|
| 课表暂存/提交/删除 | `ScheduleService`、`POST /api/student/schedule/draft`、`POST /api/student/schedule/submit`、`DELETE /api/student/schedule` | 主选 ≤4、备选 ≤2；提交时校验并写入选课名单；注册已关闭的学期禁止提交 |
| 先修/满员/时间冲突校验 | `ScheduleService` | 先修未通过拒绝；容量已满返回 `COURSE_FULL`（**通知发生在写库前**）；同一天时段重叠判定；主选与备选共同参与判定 |
| 主选/备选顺序语义 | `schedule_item`（`item_type` + `sort_order` + `promoted`） | 备选按序补位的依据；补位由成员F 的关闭注册工作流触发 |
| 视图装配 | `CourseOfferingView` | 课程班列表与先修达成（`prerequisites` 含 `passed`）、已选人数/容量、教授与时间 |
| 接口身份 | `StudentController` | 全部从 `AuthUser` 取本人身份，接口层不接收他人 ID |

### 2.2 选课调整期加退选
| 工作项 | 产出 | 说明 |
|--------|------|------|
| 加/退选 | `ScheduleService.adjustmentAdd`、`ScheduleService.adjustmentDrop`（`/api/student/adjustment/add/{offeringId}`、`/api/student/adjustment/drop/{offeringId}`） | 前置条件：注册已关闭 + 当前时间落在学期调整期；复用主选/备选上限与时间冲突校验 |
| 差额提示 | `ScheduleView.notice` | 加/退选返回差额金额文案（金额由计费服务计算），前端弹窗展示 |
| 计费联动 | 调用 `BillingService`（成员F） | 产生 ADJUSTMENT 类型交易；事务边界与计费发送解耦 |

### 2.3 学生端查询
| 工作项 | 产出 | 说明 |
|--------|------|------|
| 电子成绩单 | `GET /api/student/report-card`（`StudentQueryService`） | 按学期返回成绩（课程/学分/教授/等级）；无数据时按用例返回提示 |
| 学业记录 | `GET /api/student/transcript` | 按学期分组：课程/学分/教授/成绩；汇总学分与加权 GPA（I/未录入不计） |

| 按学期查看课表 | `GET /api/student/schedule?semesterId=` | 迭代 2 起支持按学期查看（默认当前学期；非当前学期只读） |

## 3 关键设计判断
| 判断 | 理由 |
|------|------|
| "满员通知"在写库前判定 | 题目要求"学生提交课表前实时通知"，先校验后写入才能保证语义 |
| 主选与备选共同参与冲突判定 | 否则会出现"备选与主选撞车、补位时才暴露"的隐性冲突 |
| 学生接口一律从 `AuthUser` 取本人 ID | 从接口形态上消除越权入口——没有参数就没法传别人的 ID |
| 选课类写操作锁定当前学期 | 历史学期只提供查看（只读横幅由前端呈现），避免回填历史选课数据 |

## 5 收获与不足
**收获**：
- 理解了"实时通知"这类需求的实现位置很关键：同样的校验放在写库后，语义就完全不同；
- 备选补位顺序（`sort_order` + `promoted`）让我体会到**数据结构就是业务规则**的载体；
- 与计费链路的接口约定（`BillingService`）让我第一次实践了"跨模块只暴露显式接口"。

**不足**：
- 早期把"满员通知"设计成写库后校验，后来改为提交前校验——第一遍对需求的理解偏了；
- 调整期差额提示最初只返回金额数字，学生看不出含义，后来改为完整中文文案随 `ScheduleView.notice` 返回。
